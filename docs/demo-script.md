## Pre-recording checklist

**Environment**

- [ ] Fresh terminal, `cd ~/Dev/faultline && source .venv/bin/activate`, `pip install -e .` already done, `faultline --version` prints `faultline 1.0.0`.
- [ ] `faultline lab samples/` has been run; `ls samples/` shows all captures and `labels.json`.
- [ ] `faultline bench` passes (all PASS, 0 false alarms). If anything fails, fix or drop that sample from the script before recording.
- [ ] `faultline web --no-browser` starts cleanly on 127.0.0.1:8765; a browser tab is already open on it and zoomed to ~125 % so text is legible at 1080p.
- [ ] Wireshark installed and opened once (so no first-run dialog appears on camera).
- [ ] Pre-run every command once so Python byte-code is compiled and nothing lags.
- [ ] Clear the terminal (`clear`) and shell history view before each segment; close notifications (macOS: Focus / Do Not Disturb on).
- [ ] Hide the macOS dock and menu bar clutter; close other apps; remove personal files from the Desktop if it will be visible.

**Terminal**

- [ ] Window exactly 1920×1080 (or record at 1280×720 with the same ratio). In iTerm2/Terminal: a profile with font size 18–20 (Menlo or JetBrains Mono), dark background, no transparency, ~120 columns × 34 rows at 1080p.
- [ ] Prompt shortened to something like `faultline $` (`export PS1="faultline $ "`) so paths don't eat the screen.
- [ ] `--no-color` is **not** used; the colours are part of the story.

**Files to have ready**

- [ ] `samples/mitm_rogue_dhcp.pcap`, `samples/lossy_link.pcap`, `samples/ip_conflict.pcap`, `samples/arp_spoofing.pcap`, `samples/malformed/*`, `samples/clean_office.pcap`.
- [ ] A hostile capture with a hostname like `<script>alert('xss')</script>` inside a DHCP hostname or DNS name (generated by the lab; name it `samples/malformed/xss_hostname.pcap`) <!-- VERIFY: exists -->
- [ ] An `after` capture for the diff shot (e.g. `samples/clean_office.pcap` against `samples/lossy_link.pcap`).

**Recording**

- macOS: QuickTime Player → File → New Screen Recording → select the 1920×1080 window region; microphone: built-in or headset. Or `Cmd+Shift+5`.
- Record the voice **while** doing the actions; it sounds natural and saves editing. Re-record a segment rather than fixing it in post.
- Compress to under 100 MB when done:

  ```bash
  ffmpeg -i in.mov -vcodec libx264 -crf 28 -preset slow -acodec aac -b:a 128k demo.mp4
  ```

- Upload (unlisted YouTube or Google Drive with link access), paste the link into README.md at `<!-- VIDEO_LINK -->`.

## The script

Timecodes are targets; total ≈ 4:10.

### 0:00–0:25 · Hook

**On screen:** Title card (a plain slide or the README header in a browser): "**Faultline** – Is my network broken, or is someone breaking it?" Then cut to the terminal.

**Voiceover:**

> Monday morning in a small office. The Wi-Fi is up, but every website is wrong, video calls freeze, and the printer has vanished. The office manager does the one thing everyone knows: restart the router. Here's the problem. To the person suffering it, an outage and an attack look exactly the same. "The internet is broken." And while the router reboots, the attacker who's sitting on the LAN keeps reading the traffic.

### 0:25–0:50 · The problem and the promise

**On screen:** Terminal. Type slowly: `faultline analyze samples/mitm_rogue_dhcp.pcap` but don't press Enter yet.

**Voiceover:**

> The only honest way to know what's happening is a packet capture, and reading one takes years of protocol knowledge. Faultline reads it for you. Give it a pcap and it answers three questions in plain language: what's wrong, is it a fault or an attack, and what do I fix first. With the exact packets as proof. And it's all our own code: our own capture reader, our own protocol decoders, our own detection logic. No Wireshark, no tshark, no Scapy.

### 0:50–1:50 · Demo 1: rogue DHCP + DNS hijack (web dashboard)

**On screen:**

1. Press Enter on the terminal command. Let the red **UNDER ATTACK** panel appear. Pause one second.
2. Switch to the browser on `http://127.0.0.1:8765`. Click the sample `mitm_rogue_dhcp.pcap` in the samples gallery (or upload it). <!-- VERIFY: dashboard has a samples gallery; otherwise upload -->
3. Point at the verdict, the health score, and the **Fix this first** incident card "Man-in-the-middle attack".
4. Expand the root finding `dhcp.multiple_servers` → "Rogue DHCP server". Scroll to **Why we think it's an attack** and the "Not a misconfiguration: …" line.
5. Expand the consequence `dns.hijack`. Show the evidence frame list and the evidence lines.
6. Click **Download evidence pcap** for the DNS hijack finding; open it in Wireshark; show the two DNS responses for one query ID. <!-- VERIFY: evidence download button in web UI -->

**Voiceover:**

> Let's load the capture from that office. Verdict: under attack. Not "something is slow", not forty red alerts. One incident, and a sentence a manager can act on: a device on your network put itself between your users and the internet.
>
> Faultline found two things and understood that they're one story. A second DHCP server appeared and handed out a fake DNS server. Then that fake DNS server started answering lookups with wrong addresses. The dashboard says: fix the DHCP server first; the DNS problem is a consequence.
>
> Here's the part that matters. Two DHCP servers is also what you see when someone plugs a home router into the office. So why does Faultline call this an attack and not a misconfiguration? Because it tells you. The second server advertised a different DNS, and that DNS is a regular laptop on the LAN, not the gateway. And the hijacked answers came from exactly that laptop. A home router doesn't do that. The alternative reading, and why it lost, is right here.
>
> Every finding comes with the frames. One click gives me a tiny pcap with only the evidence, and in Wireshark you can see it with your own eyes: one query, two answers, the fake one first.

### 1:50–2:30 · Demo 2: lossy Wi-Fi in the CLI (fault, not attack)

**On screen:** Terminal. Run:

```bash
faultline analyze samples/lossy_link.pcap
```

Let the yellow **FAULTY** panel show. Point at the retransmission finding, its "downstream of the capture point" line, the fix steps and the "Why we think it's a fault" indicators. Then run:

```bash
faultline diff samples/lossy_link.pcap samples/clean_office.pcap   # <!-- VERIFY: both captures must come from the same 'office' so hosts match -->
```

<!-- VERIFY: diff output reads sensibly for this pair; otherwise use a dedicated before/after pair from the lab -->

**Voiceover:**

> Second office, different complaint: video calls keep freezing. Faultline says faulty, and explicitly: no sign of an attack. Six percent of packets are being lost, and it says where: downstream of the point where we captured, between this laptop and the access point. That's the difference between "it's slow" and "it's your Wi-Fi, not the server". The fix is right there: move the access point, change channel, or plug in a cable.
>
> After the fix, you take another capture and run diff. Faultline tells you what got fixed, what persists, and whether anything new appeared. That's how you prove to your boss that the problem is actually gone.

### 2:30–3:05 · Demo 3: IP conflict vs ARP spoofing, side by side

**On screen:** Split the terminal in two panes (or run one after the other). Left:

```bash
faultline analyze samples/ip_conflict.pcap
```

Right:

```bash
faultline analyze samples/arp_spoofing.pcap
```

Highlight: both findings have the same kind `arp.duplicate_ip`; left is **FAULT "Duplicate IP address"**, right is **ATTACK "ARP spoofing"** with MITRE T1557.002. Point at the indicator bullets on each side.

**Voiceover:**

> This is the heart of Faultline. These two captures look identical to a user: two devices answering for the same IP. On the left, a printer was given a static address inside the DHCP range. Fault. Fix: move the printer. On the right, a laptop is claiming the router's address and re-announcing it every second while the real router is still alive. That's ARP spoofing.
>
> Our detectors don't decide "attack". They list evidence for each hypothesis with a weight, and one engine scores them, so every finding shows what pointed each way and why one reading won. If the evidence is balanced, the confidence says so and both readings are shown. We'd rather say "probably a conflict, check for spoofing" than cry wolf.

### 3:05–3:40 · Security segment

**On screen:** Terminal. Run in quick succession:

```bash
faultline analyze samples/malformed/truncated.pcap
faultline analyze samples/malformed/huge_caplen.pcap
faultline analyze samples/malformed/compressed_padding.pcap.gz
python scripts/fuzz.py -n 300 -q
```

Then in the browser upload `samples/malformed/xss_hostname.pcap` and show the hostname rendered as literal text in the hosts table. Then:

```bash
faultline analyze samples/mitm_rogue_dhcp.pcap --redact
```

Point at the pseudonymised addresses and the "addresses redacted" note.

**Voiceover:**

> A capture file is untrusted input, and a malicious one is a cheap way to attack the analyst. So we wrote the reader ourselves. Truncated file: it reports the corruption with the byte offset and still analyses what it read. A pcapng block claiming sixteen gigabytes: rejected before a single byte is allocated. A gzip bomb: streamed through a size guard. The fuzzer mutates real captures a few hundred times: no exception, bounded time.
>
> Reports are hardened too. This capture contains a hostname that is a script tag. In the dashboard, it's just text: strict content security policy, no external resources, everything rendered as text, never as HTML.
>
> And privacy. Payloads are never kept in memory. Passwords sent in the clear are reported by protocol only, never shown. And with redact, every address becomes a consistent pseudonym under a random key that is never written down, so you can share the report with a vendor safely.

### 3:40–4:00 · Benchmark

**On screen:** Terminal:


Let the table render. Point at the summary line: detection rate, correct fault/attack verdict rate, false alarms, clean captures quiet, hostile files handled.

**Voiceover:**

> How do we know it works? Every sample is generated by our own scenario lab, byte by byte, with labels. The benchmark runs them all: <!-- VERIFY: read the actual numbers from the screen; e.g. "thirty scenarios, every expected finding detected, every fault-or-attack verdict correct, zero false alarms on the clean and busy office captures, every hostile file handled" --> and the clean captures stay quiet, because a tool that cries wolf gets uninstalled.

### 4:00–4:15 · Close

**On screen:** README "Try it in 60 seconds" block in the browser, then the title card.

**Voiceover:**

> Try it yourself in sixty seconds: clone, pip install, faultline analyze. Python standard library for the engine, rich and Flask for the screens, nothing else. Faultline: is my network broken, or is someone breaking it? Now you can tell.
